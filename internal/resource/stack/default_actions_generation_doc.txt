Here are the exact steps, in plain English, matching the frontend's algorithm precisely (create-flow only, not the stack-upgrade flow).

Prerequisite: build the ordered workflow list
Step 1. Get the list of workflows that make up the chosen stack template revision, in the exact order the revision defines them (its WorkflowsConfig.workflows list). This ordered list is the single source of truth for everything that follows — both the ids used as action keys and the sequence used to build the dependency chains.

Step 2. For each workflow in that list, resolve two things you'll need later:

Its id — use the workflow's own id if the revision assigned one. This becomes the key you'll use for that workflow everywhere in the actions structure.
Its workflow type — fetch the referenced template's own revision and read its "source config kind." If that value is one of HELM, KUBECTL, ANSIBLE_PLAYBOOK, CUSTOM, or CLOUDFORMATION, classify this workflow as type CUSTOM. Otherwise, keep the value as-is (e.g. TERRAFORM, OPENTOFU). Cache this lookup per referenced template id so you don't re-fetch the same template twice if it's reused in multiple slots.

Generate the three default actions
Step 4. Create exactly three action containers — always these three, never more or fewer:

apply: display name "Create", description "use this action to create resources in the stack", marked as a default action, with an empty ordering map.
destroy: display name "Destroy", description "use this action to destroy resources in the stack", marked as a default action, with an empty ordering map.
plan: display name "Plan", description "use this action to plan resources in the stack", marked as a default action, with an empty ordering map.
Step 5. Fill in each action's ordering map, one entry per workflow, keyed by the workflow's id from Step 2:

For apply — walk the workflow list forward, first to last:

For each workflow, add an entry recording that its parameter is "run a Terraform apply."
If this is not the first workflow in the walk, also record that it depends on the previous workflow visited, with the condition "that workflow's latest status must be COMPLETED." The very first workflow visited gets no dependency recorded at all (not an empty one — simply omitted).

For destroy — walk the same workflow list backward, last to first:

Same entry shape, but the parameter records "run a Terraform destroy."
The first workflow visited in this backward walk (which is the last workflow in the original list) gets no dependency. Every workflow visited after that depends on whichever workflow was visited immediately before it in this backward walk — so teardown happens in the reverse of creation order, chained the same way.

For plan — walk the workflow list forward again (same direction and order as apply):

Same entry shape, but the parameter records "run a Terraform plan."
Same dependency rule as apply: first visited gets none, each subsequent one depends on the one immediately before it.
Post-process: strip parameters for non-Terraform workflows

Step 6. Once all three actions are built, do one more pass over the whole Actions object: for every workflow id you classified as CUSTOM type in Step 2, find that id inside every action's ordering map (apply, destroy, and plan) and clear its recorded parameter down to nothing (an empty parameter set) — dependencies for that entry stay untouched. This is because apply/destroy/plan have no meaning for non-Terraform step types (Helm, Kubectl, Ansible, CloudFormation) — only the dependency chain still matters for those.

Finish
Step 7. Whatever you ended up with — either the revision's own copied Actions (Step 3) or the freshly generated and cleaned one (Steps 4-6) — becomes the Actions field of the payload you submit when creating the stack, alongside the stack's name, description, tags, and its resolved workflow configuration.

That's the complete procedure — nothing else touches the Actions object between revision lookup and the create-stack API call.
